# 原始调研 · 存档设计规范与许可/导出合规

> 本文是《第三方系统选型报告》的原始调研材料之一。
> **核查基线**：Godot 官方文档 `stable` = **Godot 4.7**（4.7 于 2026-06 发布 / supported；4.8 = master；4.6 = 2026-01；4.5 起仅安全修复；4.4 及更早 EOL）。
> **抓取技巧（重要，可复用）**：`docs.godotengine.org` 的 HTML 被巨型导航淹没导致 fetch 截断 → 改用 Sphinx 源文 `https://docs.godotengine.org/en/<ver>/_sources/<path>.rst.txt` 可拿到**纯正文**。本文 20+ 个官方页面据此核实。

## 0. 三个必须纠正的事实陷阱

### 0.1 「Godot 4 默认字体不含中文」只对了一半

默认项目字体确实是 **Open Sans SemiBold**（无 CJK 字形），但官方原文：

> *"The engine automatically uses system fonts as fallback fonts, which makes it possible to display CJK characters and emoji without having to load a custom font."*

所以 Windows 上中文**通常能显示**，但字形随平台变；Linux 取决于发行版；Android 官方说 system font 加载 *"unreliable"*。

**结论仍是内嵌 Noto Sans SC + 挂 Theme，但理由要改成「可复现性 / 跨平台一致性」，不是「否则是豆腐块」**——后者会被懂行的老师当场指出错误。

### 0.2 JSON 精度是真坑

官方 JSON 文档原文：

> *"converting a Variant to JSON text will convert all numerical values to float types"*

→ **64 位随机物品 uid 存 JSON 会丢精度**，必须存成 **string**。
→ 词缀 roll 值要精确往返必须 `JSON.stringify(data, indent, sort_keys, full_precision=true)`（**第 4 个位置参数**）。

### 0.3 「4.3 才引入 DirAccess 静态绝对路径方法」是错的

逐版核对 4.0 / 4.3 / 4.7 的 `class_diraccess` 文档：`rename_absolute` / `remove_absolute` / `copy_absolute` / `dir_exists_absolute` / `make_dir_absolute` / `make_dir_recursive_absolute` / `get_files_at` / `get_directories_at` / `get_open_error` **在 4.0 就存在**。

4.3 新增的是 `create_link`/`read_link`/`is_link`/`is_case_sensitive`；4.7 新增 `create_temp`/`get_filesystem_type`/`get_drive_label`/`is_bundle`/`is_equivalent`。

→ **本项目要用的存档 API 从 4.0 到 4.7 完全一致，无版本迁移风险。**

## A. 存档系统

### A1. 官方「Saving games」教程给不了我们要的东西

官方做法：`Persist` 组 + 每节点 `save()` 返回 dict + `JSON.stringify` + `store_line` 一行一对象 + `JSON.new().parse()` 失败时用 `get_error_message()`/`get_error_line()`。

**官方教程【没有】：schema 版本号、原子写、损坏备份重建、migration、加密。** 而且它的 `set(i, node_data[i])` 批量回填对玩家可编辑文件是不安全的。

→ 设计文档那句「存档采用版本号字段。读取失败时保留旧文件并生成新存档，避免直接覆盖损坏数据」方向完全正确，**正是官方教程的空白处**。

（另：官方明确推荐**用户配置用 `ConfigFile`**，所以 settings 建议走 `user://settings.cfg`，与存档分离。）

### A3. 推荐模式

**文件布局**：

```
user://saves/profile_0.json
user://saves/profile_0.json.bak       # 上一个好版本
user://saves/profile_0.json.tmp       # 写入中间态
user://saves/profile_0.corrupt.bak    # 损坏隔离档
```

**Windows 路径（官方表格原文）**：

| 情况 | 路径 |
|---|---|
| 默认 | `%APPDATA%\Godot\app_userdata\<项目名>` |
| 开 `use_custom_user_dir` | `%APPDATA%\<项目名>` |
| 再设 `custom_user_dir_name` | `%APPDATA%\<custom_user_dir_name>` |

官方原文：`user://` *"is created automatically and guaranteed to be writable to, even in an exported project"*，而 `res://` 运行时 *"will likely be read-only"*。

**schema 结构**：

```
schema_version (int)
warehouse.slot_count = 24
items: 定长 24 数组（null 补位），每件 { uid(string!), def_id, quality(int), affixes:[{id, value, roll}] }
unlocks
tutorial_flags
settings_ref
best_runs
```

**核心流程（API 名称全部已对照 4.7 文档）**：

```
save_atomic():
    make_dir_recursive_absolute
    → 写 .tmp → flush() → close()
    → 回读 JSON.new().parse() 校验
    → copy_absolute 主档 → .bak
    → DirAccess.rename_absolute(.tmp, .json)  提交

load_slot():
    主档缺失 → 试 .bak → 否则 _fresh_profile()
    主档损坏 → _quarantine(copy_absolute 到 .corrupt.bak，
              只有隔离成功才 remove_absolute 损坏文件)
              → 试 .bak → 否则新档
    schema_version > 当前 → 拒绝读写，且绝不改写玩家文件
    schema_version < 当前 → _migrate() 链式升级
```

**关于原子性的诚实说明**：Godot 文档**只保证** *"If the destination file or directory exists and is not access-protected, it will be overwritten."*，**没有承诺**是 NTFS 级别的原子 replace。**未验证**：`DirAccess.rename_absolute` 在 Windows 上是否原子。→ **这正是「损坏恢复」必须存在而非可选的原因。**

另外官方 FileAccess 文档明说：**F8 强杀进程时文件不会自动关闭**，需主动 `flush()`。

**加密**：`FileAccess.open_encrypted_with_pass(path, flags, pass: String)`；`FileAccess.open_encrypted(path, flags, key: PackedByteArray, iv := PackedByteArray())`，文档原文 *"The provided key must be 32 bytes long."*

**工程判断（非文档结论）**：口令硬编码在导出的 PCK 里，玩家反编译即可得，**加密只能防记事本随手改，不是反作弊**。课程单机项目**建议不做加密**，把精力放在版本号 + 恢复上。

**已核对的 API 清单**：

- `FileAccess`：`open` / `get_open_error` / `file_exists` / `store_string` / `get_as_text` / `store_line` / `get_line` / `get_file_as_string` / `get_file_as_bytes` / `get_sha256` / `get_md5` / `store_var(v, full_objects=false)` / `get_var(allow_objects=false)` / `open_encrypted` / `open_encrypted_with_pass` / `open_compressed` / `flush` / `close` / `get_error`
- `DirAccess`：`open` + 全部 `*_absolute` 静态变体
- `JSON`：`stringify(data, indent="", sort_keys=true, full_precision=false)` / `JSON.new().parse()` + `data` / `get_error_message()` / `get_error_line()` / `parse_string()`（**失败返回 null 且不报错**）/ `from_native` / `to_native`

### A4. JSON vs `.tres` vs `var_to_bytes`

- **JSON ✅ 推荐**：数据全是原生类型；24 格物品体积极小，「文件更大」无影响；文本可 diff / git 管理 / 崩溃后人眼可修。
- **`.tres` / ResourceSaver ❌ 不要用于玩家可写目录**：`Resource` 可携带 `script` 属性，等于让玩家可写的文件决定加载哪个脚本。
- **`var_to_bytes` / `store_var` ⚠️**：官方明确更小、支持更多类型、自定义类逻辑更少；但二进制不可读不可 diff、迁移困难，且 **`full_objects=true` / `allow_objects=true` 是 RCE 级坑**。

**安全性的诚实核查结果（重要，别照抄网上说法）**：

- ✅ 已确认官方明文警告（`FileAccess.get_var`）：*"Deserialized objects can contain code which gets executed. Do not use this option if the serialized object comes from untrusted sources to avoid potential security threats such as **remote code execution**."*
- ✅ 已确认：`JSON.to_native` / `JSON.from_native` 的 objects *"are ignored for security reasons"*，除非显式开启。
- ✅ 已确认：官方「Exporting packs, patches, and mods」有独立 **"Security concerns"** 章节（三种攻击场景 + 建议用非对称加密 + `Crypto` 类签名）。
- ❌ **未验证**：完整读了 4.7 的 `class_resourceloader.rst.txt`，**其中并没有**「加载不受信任 `.tres`/`.res` 会执行任意代码」的警告原文。→ 「ResourceLoader 读不可信资源不安全」这个结论**在本报告没有官方针对性引文**；能确证的只有「反序列化对象可含被执行代码」适用于 `FileAccess.get_var(allow_objects=true)`。

**「JSON 玩家可改」要不要紧**：单机课程作业**不要紧**，甚至加分（助教能直接看懂存档）。但别把存档字段当敏感判定的唯一来源；涉及排行榜 / 联机时存档必须视为不可信输入。

## B. 许可与导出合规

### B1. 许可证规则（条件栏均对照 choosealicense / OFL-FAQ 正文）

| 许可证 | 必须做的 | 对我们的含义 |
|---|---|---|
| MIT | 仅保留版权声明 + 许可文本 | 可闭源商用；复制 MIT 代码**必须保留出处** |
| Apache-2.0 | 版权/许可通知 **＋ State changes（标注改动）＋ 有 NOTICE 要一并携带**；含专利授权，**不含商标权** | 比 MIT 多两件事 |
| BSD-2 | 版权/许可；**二进制分发时**须在「documentation and/or other materials」中重现声明 | 导出 `.exe` → **必须放在随包文档/关于页**，不能只在源码仓库放 |
| MPL-2.0 | **"Same license (file)"**：覆盖的**单文件**及修改继续 MPL；Larger Work 可用其他条款 | **文件级弱 copyleft**：改过的 `addons/` 内文件要开源，**游戏主体不受影响** ← 想要弱 copyleft 时最优解 |
| LGPL-3.0 | Disclose source + notice + Same license(library) + State changes；**通过接口使用的 Larger Work 可不同条款** | GDScript 用不上；若用 LGPL 的 GDExtension 原生库，动态 `.dll` 已基本满足可重链接要求 |
| GPL-3.0 | **Disclose source + Same license + State changes + notice** | 见下 |
| CC0-1.0 | **Conditions 栏为空**（无任何义务） | 最省事，仍建议登记来源 |
| CC-BY-4.0 | **署名 + 版权声明 + 许可声明 + 免责声明声明 + 指向素材的 URI/超链接**；改动需标注 | 比「写个作者名」要求多；**必须给素材本身的链接** |
| CC-BY-SA-4.0 | CC-BY 全部 ＋ ShareAlike：改编后的 Adapter's License 必须是同 License Elements 的 CC 或兼容许可 | ⚠️ 会传染**改编后的那份素材**；**建议原样使用不改编** |
| OFL-1.1 | 见 B1.2 | 字体首选 |

#### B1.1 GPL 与 `addons/` 插件——本报告最需谨慎的一条

GPL-3.0 §5(c) 原文：

> *"You must license the entire work, as a whole, under this License to anyone who comes into possession of a copy. This License will therefore apply … to the whole of the work, and all its parts, **regardless of how they are packaged**."*

→ **这句 "regardless of how they are packaged" 直接否掉了「塞进 `addons/` 子目录就算独立作品」的常见自救说法。**

但 §5 标题是 *"Conveying **Modified** Source Versions"*，真正决定传染范围的是「衍生作品 / 基于」的界定，而 GPL-3.0 正文**没有**像 LGPL 那样给出清晰的「接口 vs 链接」界线。→ **原封不动的 GPL 插件被专有游戏引用并一起分发，属法律灰区。标记为 未验证/有争议。**

**可操作结论**：

- ✅ **绝对不要引入 GPL/AGPL**
- ✅ 已引入就移除重写，或准备把**整个项目以 GPL-3.0 释出**
- ✅ 安全替代 MIT / Apache / BSD / MPL / CC0 / OFL
- ⚠️ **引入前读仓库根 LICENSE 本体**（核 GUT 时就遇到 GitHub 自动识别失败、`license: null` 但实际 MIT 的情况；反向「README 写 MIT、LICENSE 写 GPL」的仓库也真实存在）

#### B1.2 OFL 字体（OFL-FAQ 1.1-update7 正文）

- ✅ 打包进游戏**不会**让游戏变成 OFL。FAQ 1.3：*"No. Only the portions based on the Font Software are required to be released under the OFL. The intent of the license is to allow aggregation or bundling with software under restricted licensing as well."*
- ✅ 可以卖含 OFL 字体的软件包（FAQ 1.4 明确列 "games and entertainment software"）
- ✅ **不用为「使用」字体而署名**（FAQ 1.1.2：*"No. Font authors may appreciate being mentioned … but that is not required."*）← **与很多教程说的「OFL 必须署名」相反**
- ✅ 打包/内嵌时可不必附完整 OFL 文本（FAQ 1.10）；FAQ 1.20 建议**至少**在 About 框给出「版权声明 + 许可声明 + 许可文本」
- ⚠️ 不能只卖字体本身（1.6）；**改了字体必须改内部名**（RFN，5.2/5.9）
- 🤖 **与「AI 使用日志」直接相关**：FAQ **1.25**——用 AI/ML 从含 OFL 源文件的训练数据生成的字体 *"should be considered a derivative work"*，**必须继续按 OFL 发布**。（FAQ 1.26：AI 生成**非字体**图形等同普通使用，不受此限。）

### B2. `素材来源与许可.md` 字段规范（评分点）

表格列建议：`名称 | 作者/组织 | 许可证 | 来源URL | 引用版本(commit/tag) | 获取日期 | 使用位置 | 是否修改 | 署名要求`，按「代码/插件、美术、音频、字体」分表。

- **许可证写 SPDX 标识符**（`MIT`/`Apache-2.0`/`BSD-2-Clause`/`MPL-2.0`/`LGPL-3.0-or-later`/`GPL-3.0-only`/`CC0-1.0`/`CC-BY-4.0`/`CC-BY-SA-4.0`/`OFL-1.1`），不要只写「免费」
- **来源 URL 指向素材详情页**，不是 CDN 直链（会失效，且 CC-BY 要求的是「指向素材的 URI」）
- **代码/插件必须记 commit hash 或 tag**（仓库会变、许可证会变）
- **获取日期 YYYY-MM-DD** 是审计链关键（证明你当时拿的是哪个版本）
- 保留一节 **「未能确认来源的素材（必须清零后发布）」**

**许可证文本放哪（官方 6 选 1 即可）**：Credits 界面 / 专门的「开源许可」菜单 / `print()` 输出日志（iOS 不行）/ 随包文件 / 印刷手册 / 链接（官方认为指向 `godotengine.org/license` 的链接 *"would be an acceptable way to satisfy the license terms"*）。

省事技巧：`Engine.get_license_text()`、`Engine.get_license_info()`、`Engine.get_copyright_info()`；把 Godot 的 `COPYRIGHT.txt` 一起分发并**重命名为 `GODOT_COPYRIGHT.txt`**。

✅ 好消息（官方原文）：*"Your games do not need to be under the same license. You are free to release your Godot projects under any license and to create commercial games with the engine."*

⚠️ **别忘了 Godot 自己的 MIT 文本**（官方给了现成模板）。

### B3. Windows 导出 + 中文字体

**导出（已核对）**：`data.pck` + 特化二进制；架构 `x86_64`(默认) / `x86_32`(不推荐) / `arm64`(不能在普通 x86_64 上跑)；图标自动转 ICO；**PCK 内嵌上限约 3.89GB**。

- ⚠️ **非资源文件默认不打包**（FileAccess 文档原文）→ 把 Import 改为 **"Keep File (exported as is)"**，或在导出对话框 non-resource filter 加 `*.txt`。**直接影响**：`res://data/affixes.json` 这种配置表**导出后可能读不到**，建议改 `.tres`/`.gd` 常量表或加过滤器。
- ⚠️ **导出后 `res://` 目录列举结果会变**（DirAccess 文档原文：只返回 `*.gd`/`*.import` 等）→ 不要靠遍历 `res://` 找资源，用 `ResourceLoader.list_directory()`。
- ⚠️ **F8 强杀 → 文件不自动关闭** → 定期 `flush()` + 靠损坏恢复兜底。

**代码签名（已核对官方原文）**：*"Godot is capable of automatic code signing on export. To do this you must have the **Windows SDK** (on Windows) or **osslsigncode** (on any other OS) installed. You will also need a **package signing certificate**…"*

设置两处：编辑器设置 **Export > Windows > Sign Tool**；导出预设 **Options > Code signing**（`Enabled=true` + `Identity=证书`）。CI 环境变量：`GODOT_WINDOWS_CODESIGN_IDENTITY_TYPE` / `_IDENTITY` / `_PASSWORD`、`GODOT_SCRIPT_ENCRYPTION_KEY`。

❌ **未验证**：该官方页面**没有出现 "SmartScreen" 字样**，也未讨论「未签名 exe 弹『Windows 已保护你的电脑』」的后果。「未签名→SmartScreen 警告、需 EV/OV 证书+累积信誉才能消除」标记 **未验证**。

保守建议：课程阶段用 zip + 说明（「未签名，提示未知发布者时点『更多信息→仍要运行』」），公开发布再考虑证书（**注意证书是持续付费**）。

**中文字体（官方原文已核对）**：

1. 默认字体 *"Open Sans SemiBold"* → 确认引擎内置默认字体不含中文
2. 但 *"The engine automatically uses system fonts as fallback fonts, which makes it possible to display **CJK characters** and emoji without having to load a custom font."*
3. 系统字体仅 Windows/macOS/Linux/Android/iOS，**Android 官方说 unreliable**，Linux 取决于发行版
4. **`SystemFont` 资源**可指定字体名或别名；官方别名表：Windows 上 `sans-serif`→**Arial**、`serif`→Times New Roman、`monospace`→Courier New
5. **Fallback 做法**：双击字体 → **Advanced Import Settings** → 右侧 **Fallbacks** → `Array[Font] (size 0)` → **Add Element**；**Base Font 留空可「默认项目字体 + 补中文字体」**
6. **官方字体版权警告原文**：*"Fonts are covered by copyright. **Double-check the license of a font before using it, as not all fonts allow commercial use without purchasing a license.**"*
7. 系统字体不进 PCK 的额外好处（原文）：*"this avoids licensing issues that would occur if **proprietary** system fonts were distributed alongside the project"*
8. `FontFile.load_dynamic_font()` 支持 TTF/OTF/WOFF/WOFF2/PFB/PFM；`load_bitmap_font()` 支持 BMFont
9. *"Since Godot 4.0, font sizes are no longer defined in the font itself but are instead defined in the node that uses the font"* ← 网上「每种字号要复制一份字体资源」是 Godot 3 时代过时做法

**推荐方案**：下载 Noto Sans SC / Source Han Sans（均 OFL-1.1）→ 新建 `res://ui/main_theme.tres` 设 **Default Font** → Project Settings **GUI > Theme > Custom** 指向它 → 保留 `res://fonts/OFL.txt` 并在「开源许可」界面列出 → 登记进 `素材来源与许可.md`。

**性能**：用 **Advanced Import Settings → Pre-render Configurations → "Glyphs from the Text"** 粘贴全部会出现的中文点 "Shape Text and Add Glyphs"（最省体积）；⚠️ 官方提醒预渲染列表**不会随文案更新自动更新**。做描边可开 **MSDF**（官方：MSDF Pixel Range ≥ 2× outline size），但 **MSDF 不能开 LCD 亚像素抗锯齿**，且自相交轮廓字体会渲染错误 → 中文开 MSDF 前务必先试渲染。

**`user://` 与重装**：✅ 路径已核实（见 A3）。✅ 官方原文 `user://` *"guaranteed to be writable"*。
⚠️ **未验证（推论）**：官方**没有**明述「卸载/重装游戏会保留 `%APPDATA%` 下存档」；逻辑上因路径不在安装目录，Windows 常规卸载不会删它（除非安装器主动清理 AppData）。

⚠️ **反向大坑**：`application/config/name` **就是目录名**——**中途改项目名会让 `user://` 指向新目录，玩家存档「消失」**。发布后不要改；要改必须写目录迁移。

✅ 实用技巧：`ProjectSettings.globalize_path("user://")` + `OS.shell_open()` 一键打开存档目录（官方 data_paths 页就这么建议的），建议做进开发者菜单。

### B4. 陷阱清单（最关键 8 条）

1. **64 位 uid 存 JSON 丢精度** → 存 string
2. **不传 `full_precision=true`** → 词缀值往返不等
3. **无 tmp+rename** → 断电丢档
4. **损坏档直接 WRITE 覆盖** → 先 `copy_absolute` 隔离，**隔离成功才允许覆盖**
5. **存档做成玩家可写 `.tres`/带 `script`** → 加载即执行代码
6. **`get_var(allow_objects=true)` / `store_var(..., true)`** → 官方明文 RCE 警告
7. **`res://data/*.json` 当配置表** → 导出后读不到
8. **改 `application/config/name`** → 存档「消失」

另：⑨ 测试直接写 `user://saves/` 会洗掉玩家存档；⑩ CI 里把 GUT(0/1) 与 GdUnit4(0/100/101) 的退出码当成一样。
