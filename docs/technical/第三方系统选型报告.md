### 0.3 「Godot 4」不等于「能在 4.7 上跑」——两个必查红旗

1. **Godot 3.x 时代的代码**：凡出现 `KinematicBody2D` / `yield` / `Spatial` / `JSONParseResult` 的仓库或代码片段，在 Godot 4 下**直接报错**。搜索排名靠前的 [`rdmtt/Godot-3.1-Advanced-Save-System`](https://github.com/rdmtt/Godot-3.1-Advanced-Save-System)（69★）就是**仅 Godot 3.1**。
2. **文档示例是旧 API**：最典型的是 `peter-kish/gloot` 的 README `deserialize()` 示例仍写 `var res: JSONParseResult = JSON.parse(json)`——Godot 4 已删除 `JSONParseResult`，**照抄必崩**。

另外两条**版本下限**（我们锁 4.7，全部满足，但若有人降版本会立即报废）：

- `phantom-camera` / `trauma-gd` → 最低 **4.4**
- `health-hitbox-hurtbox` → 最低 **4.5**
- `limboai` → 最低 **4.6**
- `Maaack` 全系 → v1.6.0 起最低 **4.4**（release notes 原文：*"This release breaks compatibility with Godot 4.3."*）

> ⚠️ **请把「全员固定 Godot 4.7」写进 README 并设为硬性约定**，这正是策划案 §1 那句「全员固定使用同一小版本」要保护的东西。

## 2. 存档系统（对应策划案 §11.4 / §13.7）

### 2.1 结论：自研，不用插件

策划案 §13.7 对存档提出四条硬要求：**版本号字段 / 自动存档时机 / 读取失败保留旧文件 / 不覆盖损坏数据**。

调研了 12 个 Godot 4 存档插件（均核过许可证），结论是**自研最合适**，理由：

- 你们的存档是**纯数据**（24 格物品数组、解锁标记、bool flag、纪录），**不需要**「场景里任意节点状态自动序列化」——而主流插件（GDSave / SaveKit / game_state_saver）的主要价值恰恰在这个我们用不上的方向。
- 真正难的三点（schema 迁移 / 原子写 / 损坏时留旧档）**各 10–30 行就能写对**，代码量小到三个人都能读懂——这在课程答辩与代码评审里是加分项。
- 零依赖、零版本漂移、零许可证顾虑。

### 2.2 现成插件的实际问题（供你们自己做最终判断）

| 项目 | Star | 为什么不当主方案 |
|---|---:|---|
| [`youssof20/savestate`](https://github.com/youssof20/savestate) | 18 | 需求逐条命中、且作者实测 **4.7.2**，但**2026-04 才创建、18★、1.0→2.0 API 不兼容变更**。要用必须锁死 2.0.0 并把 addon 目录提交进版本库 |
| [`locker-godot/locker`](https://github.com/locker-godot/locker) | 60 | 架构正统（`StorageAccessor` / `AccessStrategy`），但**原子写策略未文档化**，仍需自己补 |
| [`AdamKormos/SaveMadeEasy`](https://github.com/AdamKormos/SaveMadeEasy) | 220 | Star 最多但**2025-01 后停滞**；密钥由**玩家 OS ID 派生**，同机多人测试时存档不可移植；无 schema 迁移 |

### 2.3 推荐实现（已对照官方文档与 demo 逐条核实）

**存储格式建议用 `ConfigFile`，而不是 JSON。** 工作区内的 Godot 官方 demo 给出了直接依据：

- `loading/serialization/save_load_json.gd:4-6` 原文：*"integers get converted into doubles, and to store Vector2 and other non-JSON types you need to convert them, such as to a String using `var_to_str`"*
- `loading/serialization/save_load_config_file.gd:2` 原文：*"ConfigFile can store any Variant type except Signal or Callable"*

对我们的意义：物品的 `quality:int` 用 JSON 读回会变成 `3.0`，24 格 × 每件 3 个词条数值会满地都是 `int()` 转换和潜在 bug；`ConfigFile` 保留原生类型，且**仍然人类可读**（第 10 周内测排障速度直接受益）。

#### ⚠️ 如果你们最终还是选 JSON：两个会静默损坏存档的精度陷阱

这是本次调研中**代价最高的一条发现**，也是「为什么推荐 ConfigFile」的最强论据：

1. **官方 JSON 文档原文**：*"converting a Variant to JSON text will convert all numerical values to float types"*
   → **64 位随机物品 uid 存成 JSON 数字会丢精度**，读回来是另一个 uid。
   → **必须把 uid 存成 string**：`{"uid": "18446744073709551615"}`，而不是 `{"uid": 18446744073709551615}`。
   → 阴险之处：小数据量测试完全正常，等仓库攒到几十件、或 uid 高位恰好非零时才炸，表现为「装备凭空消失 / 串号」——正是策划案 §20 风险表点名的「合成规则错误 → 复制物品」。
2. **词缀 roll 值要精确往返，必须开第 4 个参数**：`JSON.stringify(data, indent, sort_keys, full_precision=true)`。默认 `full_precision=false` 会截断精度，词条数值往返后可能不等，导致「同名词条继承数值较高者」（§5.5）判错。

**`ConfigFile` 天然没有这两个问题**（存的是原生 Variant），这就是采用它的核心理由。

**存档骨架（可直接用，~90 行核心）：**

```gdscript
# res://autoload/save_manager.gd   (autoload 名: SaveManager)
extends Node

const SCHEMA_VERSION := 1
const SAVE_PATH  := "user://save_0.cfg"
const BACKUP_PATH := "user://save_0.cfg.bak"

func save_game(data: Dictionary) -> bool:
    data["schema_version"] = SCHEMA_VERSION            # ① 版本字段
    data["saved_at"] = Time.get_datetime_string_from_system()

    var tmp := SAVE_PATH + ".tmp"
    var cfg := ConfigFile.new()
    for section: String in data:
        cfg.set_value(section, "value", data[section])

    # ② 先写临时文件，绝不直接覆盖正本
    if cfg.save(tmp) != OK:
        push_error("存档写入临时文件失败")
        return false

    # ③ 旧档降级为 .bak，而不是被销毁
    if FileAccess.file_exists(SAVE_PATH):
        DirAccess.remove_absolute(ProjectSettings.globalize_path(BACKUP_PATH))
        DirAccess.rename_absolute(SAVE_PATH, BACKUP_PATH)

    # ④ 原子替换（DirAccess.rename_absolute 目标存在会被覆盖）
    return DirAccess.rename_absolute(tmp, SAVE_PATH) == OK

func load_game() -> Dictionary:
    if not FileAccess.file_exists(SAVE_PATH):
        return new_profile()
    var cfg := ConfigFile.new()
    var err := cfg.load(SAVE_PATH)
    if err != OK:
        # ⑤ 绝不覆盖损坏文件，改名留证后生成新档
        var broken := SAVE_PATH + ".corrupt_%d" % Time.get_unix_time_from_system()
        DirAccess.rename_absolute(SAVE_PATH, broken)
        push_warning("存档损坏(%d)，已备份为 %s，创建新存档" % [err, broken])
        return new_profile()

    var data := {}
    for section: String in cfg.get_sections():
        data[section] = cfg.get_value(section, "value")

    var v := int(data.get("schema_version", 1))
    while v < SCHEMA_VERSION:
        data = _migrate(v, data)
        v += 1
    return data

func _migrate(from_version: int, data: Dictionary) -> Dictionary:
    match from_version:
        1: data["warehouse"] = data.get("warehouse", [])
    return data

func new_profile() -> Dictionary:
    return {
        "schema_version": SCHEMA_VERSION,
        "warehouse": [],          # Array[Dictionary]: {uid, slot, quality, affixes:[{id,value}]}
        "blackbox": {},           # 黑匣：保险核心 或 受保护装备（互斥）
        "unlocks": {},            # 已救援 NPC / 已解锁核心掉落资格
        "tutorial_flags": {},     # 教学提示完成状态
        "records": {},            # 最佳通关记录
    }
```

### 2.4 八个已核实的坑

1. **`FileAccess.WRITE` 会先把文件截断为 0 长度** → 崩溃窗口的根因，必须 `.tmp` + `rename_absolute`。
2. **`JSON.parse_string` 失败只返回 `null`，无错误详情** → 需要诊断信息时用 `JSON.new().parse()` 配 `get_error_message()` / `get_error_line()`。
3. **`store_var(full_objects=true)` / `get_var(allow_objects=true)` 有官方 RCE 警告**——原文「Deserialized objects can contain code which gets executed」。**永远传 `false`**。（官方 `save_load_config_file.gd:4-5` 同样警告 ConfigFile 存 Object 的风险。）
4. **设置必须与存档分离**：策划案 §11.4 把「设置选项」和「仓库组件」并列，但两者生命周期不同。设置单独走 `user://settings.cfg`，否则改音量会触发仓库自动存档。
5. `FileAccess` 在**强杀进程**时不会正常关闭 → 关键节点主动 `flush()`。
6. **自动存档要加去抖**：`_dirty = true` → 等 1–2 秒无新修改 → 再落盘。否则合成时连续操作会反复写盘。
7. **高版本存档必须拒绝读写，且绝不改写玩家文件**。玩家回滚到旧版程序时，旧版会读到新格式存档——若不判断 `schema_version > 当前版本`，旧程序会「迁移」出一个残缺存档并覆盖新存档，**造成不可逆的数据丢失**。处理：检测到高版本 → 弹提示「此存档由更新版本创建」→ 只读或拒绝加载，**一个字节都不写**。
8. **损坏文件的隔离顺序不能错**：先 `copy_absolute` 到 `xxx.corrupt.bak`，**只有隔离成功之后才允许删除原文件**。若先删再拷，一次 IO 失败就等于永久销毁玩家进度。（策划案 §13.7 那句「读取失败时保留旧文件」的严格实现就是这个顺序。）

### 2.4.1 一个好消息：存档 API 从 Godot 4.0 到 4.7 完全一致

本次逐版核对了 4.0 / 4.3 / 4.7 的 `class_diraccess` 文档：`rename_absolute` / `remove_absolute` / `copy_absolute` / `dir_exists_absolute` / `make_dir_absolute` / `make_dir_recursive_absolute` / `get_files_at` / `get_directories_at` **在 4.0 就已存在**。

4.3 新增的是 `create_link` / `read_link` / `is_link` / `is_case_sensitive`；4.7 新增 `create_temp` / `get_filesystem_type` / `get_drive_label` / `is_bundle` / `is_equivalent`。

> ✅ **结论：本项目要用的存档 API 没有任何版本迁移风险**——这降低了「万一第 7 周被迫降到 4.4」的代价。

### 2.4.2 关于「原子写」的一个必须诚实说明的点

Godot 文档对 `rename_absolute` **只承诺**：*"If the destination file or directory exists and is not access-protected, it will be overwritten."*——**并没有承诺**这是 NTFS 级别的原子 replace。`rename_absolute` 在 Windows 上是否真原子，**本次未验证**。

这意味着：**「损坏恢复」不是可选加分项，而是原子写不可靠时的唯一保险。** §2.3 骨架里的隔离 + `.bak` + 新档兜底三条路径必须全部实现。

### 2.5 自动存档挂点（对应策划案 §13.7）

撤离成功 / 合成完成 / 仓库整理完成 / NPC 获救 / 核心掉落资格解锁 / 设置修改 —— 六处各调一次 `mark_dirty()` 即可。

### 2.6 存档系统怎么测（对应策划案 §20「合成规则错误」风险）

两个可用的 Godot 4 测试框架（都 MIT、都支持无头 CLI）：

| 框架 | 许可证核实方式 | 无头命令 | **退出码** |
|---|---|---|---|
| [bitwes/Gut](https://github.com/bitwes/Gut) | ⚠️ **GitHub API 的 `license` 字段是 `null`**，但 `addons/gut/LICENSE.md` 原文是 MIT（*"The MIT License (MIT) Copyright (c) 2018 Tom "Butch" Wesley"*）——**别被 API 误导** | `godot -d -s --path "$PWD" addons/gut/gut_cmdln.gd -gexit` | **0 = 全通过，1 = 有失败** |
| [godot-gdunit-labs/gdUnit4](https://github.com/godot-gdunit-labs/gdUnit4)（旧地址 `MikeSchulze/gdUnit4` 会 302） | API `license.key == "mit"` | 先 `setx GODOT_BIN <godot.exe>`，再 `./addons/gdUnit4/runtest -a /myProject/test` | **0 = 全通过，100 = 有失败，101 = 有警告** |

> ⚠️ **CI 里混淆这两个退出码会让失败的测试静默通过**——GUT 的 `1` 与 GdUnit4 的 `100/101` 不能当同一个东西处理。

**存档必测 8 条**（这个清单本身就是答辩素材）：

1. 往返一致（浮点精度 + uid 字符串不变）
2. `schema_version` 缺失 → 判为损坏
3. **版本高于程序 → 拒绝且不改写文件**（对应坑 7）
4. 空文件 / 半截内容 / 顶层非 Dictionary → 隔离 + 新建
5. `.tmp` 残留不影响读取
6. 存档目录不存在时自动创建
7. 迁移链幂等（跑两次结果相同）
8. 隔离文件名冲突时递增编号，不覆盖已有隔离档

> 🔧 **关键设计**：`SaveManager` 的根目录必须是**可注入变量**（`var base_dir := "user://saves/"`），测试时指向 `user://test_saves/`。**否则跑一遍测试就会洗掉玩家存档。**

#### 3.3.3 关于「引擎会不会自动兜底」——一条必须说清的事实

> ⚠️ 如果把「必须嵌字体」的理由写成「否则是方块」，**会被懂行的老师当场纠正**。

1. Godot 默认项目字体是 **Open Sans SemiBold**，确实不含 CJK 字形。
2. **但引擎会自动用系统字体做 fallback**。官方原文：*"The engine automatically uses system fonts as fallback fonts, which makes it possible to display CJK characters and emoji without having to load a custom font."* —— Windows 上中文**通常能正常显示**。
3. **正确的理由是「跨平台可复现性与美术一致性」**：SystemFont 不进 PCK，字形/字重随机器变；Linux 取决于发行版；Android 官方明确说 system font 加载 *"unreliable"*。而且**像素字体必须用我们指定的那一套**，靠系统兜底出来的黑体完全不是我们要的观感。
4. 另有一个依然成立的坑：**一旦指定了缺乏中文覆盖的主题字体，渲染结果是空白框且不报错**。

#### 3.3.4 落地步骤

1. 选定的字体放进 `res://assets/fonts/`；后续再把最终使用的字体复制到 ASCII 子目录中
2. 新建 `res://ui/main_theme.tres`，设 **Default Font**
3. `Project Settings > GUI > Theme > Custom` 指向它
4. 字体导入的 *Advanced Import Settings* → 右侧 **Fallbacks** → `Add Element` 挂第二套（**Base Font 留空可表达「默认项目字体 + 补中文字体」**）
5. 保留各字体的 `OFL.txt`，并在「开源许可」界面列出
6. **导出必须让字体进 PCK**

**体积与画质**：用 *Advanced Import Settings → Pre-render Configurations → "Glyphs from the Text"* 把全部会出现的中文粘进去点 *Shape Text and Add Glyphs*（最省体积）；⚠️ 官方提醒**预渲染列表不会随文案更新自动更新**——后期加文案要重新加字形。做描边可开 MSDF（官方建议 MSDF Pixel Range ≥ 2× outline size），但 **MSDF 不能开 LCD 亚像素抗锯齿**，且自相交轮廓字体会渲染错误 → **点阵字体开 MSDF 前务必先试渲染**（点阵字体开 MSDF 尤其容易出问题）。

> 📌 **第 7 周和第 12 周的验收务必包含「换一台非开发电脑检查中文显示」**——策划案 §16 第 816 行已列了「检查字体」，这里给出的是具体做法。

### 3.4 背包数据层：gloot 可选

[`peter-kish/gloot`](https://github.com/peter-kish/gloot)（MIT, 982★，v3.0.2 release notes 第一条即 *"Update to Godot 4.7"*）：

- `InventoryItem` / `Inventory` / `GridConstraint`（物品 `size: Vector2i`）/ `ItemSlot`（→ 黑匣槽）
- **所有类都有 `serialize()` / `deserialize()`** → 直接进存档
- `Prototree` 是 JSON 原型且支持 `inherits` → 可承载「同品质合成升阶」的原型继承

⚠️ **两个坑**：README 的 `deserialize()` 示例是 **Godot 3 写法**（`JSONParseResult`，见 §0.3）；v2 → v3 **不向后兼容**，网上多数教程是 v2。

**判断**：如果你们只要「24 格仓库 + 4 个装备槽 + 能存盘」，**自己写 200 行 `Dictionary` + `Resource` 很可能比接 gloot 更快**。gloot 的价值在拖拽/堆叠/旋转等复杂交互上——第 8 周若觉得背包 UI 工作量大，再评估引入。

## 5. 关卡、AI 与掉落（对应策划案 §8 / §9 / §10）

### 5.1 房间生成：自己写（1.5–2 人日，150–250 行）

现成生成器解决的是**相反的问题**（自由拓扑随机房间），而我们要的是「从 8 个手搓模板里挑并拼接」。推荐做法：

1. 每个模板一个 `.tscn`，内部用固定命名的 `Marker2D` 定义槽位（`Slot_N` / `Slot_E` / `Slot_S` / `Slot_W`）。
2. 每个模板配一个 `RoomTemplateData`（Resource）：房间尺寸、可用槽位方向、`region_tag`（combat / corridor / service）。
3. 拼接用「槽位匹配表」+ `Dictionary[Vector2i, RoomInstance]` 占用网格防重叠——**确定性、可复现、好调试**。
4. **导航**：每个模板场景内预置 `NavigationRegion2D` 并**在编辑器期烘焙**（存进 `.tscn`），运行时把实例化的多个 region 放进**同一个 NavigationServer2D map** 自动合并成连通图 → 天然满足「不运行时烘焙」。
5. 生成时约束「至少 2 个 combat 房间」，复用 phantom-camera 的 priority 做区域切换。

> ✅ **第 1 周花 30 分钟做一个「多 region 同 map 连通性冒烟测试」**——这是整条路线唯一的技术假设，早验证早安心。

**仅当你们放弃手搓模板、改走全程序化时**，才考虑 [`alexishachemi/godot-procgen`](https://github.com/alexishachemi/godot-procgen)（MIT, 4.5+, 纯 GDScript, 9★）。

## 6. Windows 导出与合规（对应策划案 §16 第 12 周、§21）

> 这一节是本报告里**唯一会在「代码全对、编辑器里跑得很好」的情况下仍然让交付失败**的部分。策划案 §20 风险表那条「导出或存档失败 → 仅编辑器内可运行」讲的就是这些。

### 6.1 四个会让人措手不及的导出坑

1. **⚠️ `res://data/*.json` 当配置表 → 导出后读不到。**
   官方 FileAccess 文档原文：非资源文件默认**不打包**。你们策划案 §14 目录结构里的 `data/` 如果放 JSON 配置表，在导出包里会直接消失。
   **解法**：改用 `.tres`（自定义 Resource，正好符合策划案 §13.3 的建议）或 `.gd` 常量表；或把 Import 改为 **"Keep File (exported as is)"**；或在导出对话框的 non-resource filter 加 `*.json`。
   **建议直接用 `.tres`**——策划案 §13.3 本来就规划了 `WeaponComponentData` / `AffixData` 等自定义 Resource，两者正好合一。

2. **⚠️ 导出后 `res://` 目录列举结果会变。**
   `DirAccess` 在导出包里只返回 `*.gd` / `*.import` 等条目。**不要靠遍历 `res://` 去找资源**（比如「扫描 data/ 目录自动加载所有词缀」这种写法在编辑器里能跑、导出后静默返回空列表）。用 `ResourceLoader.list_directory()`，或干脆用「显式清单」的方式列出要加载的资源。

3. **⚠️ 改 `application/config/name` 会让玩家存档「消失」。**
   这个值**就是 `user://` 的目录名**。现在 `project.godot` 里是 `config/name="五角场热线"`——如果第 11 周有人「顺手优化一下项目名」，所有人的存档会指向一个新目录，表现为「进度没了」。
   **规则：发布后不要改项目名。** 必须改时，要写目录迁移逻辑。

4. **F8 强杀进程 → 文件不自动关闭。** 这就是 §2.4 坑 5 的导出侧体现：关键节点主动 `flush()`，并依赖损坏恢复兜底。

### 6.2 `user://` 实际落在哪（已核实）

| 情况 | Windows 路径 |
|---|---|
| 默认 | `%APPDATA%\Godot\app_userdata\<项目名>` |
| 开了 `use_custom_user_dir` | `%APPDATA%\<项目名>` |
| 再设 `custom_user_dir_name` | `%APPDATA%\<custom_user_dir_name>` |

官方原文：`user://` *"is created automatically and guaranteed to be writable to, even in an exported project"*，而 `res://` 运行时 *"will likely be read-only"*。

> 💡 **实用技巧**：做一个开发者菜单项，用 `ProjectSettings.globalize_path("user://")` + `OS.shell_open()` 一键打开存档目录——官方 data_paths 文档就是这么建议的。第 10 周内测时能省掉大量「我的存档在哪」的沟通。
>
> ⚠️ **未验证**：官方没有明说「卸载/重装游戏会保留 `%APPDATA%` 下的存档」。逻辑上因为路径不在安装目录，Windows 常规卸载不会删它——但这是**推论，不是官方承诺**。

### 6.3 代码签名与 SmartScreen

官方文档已核实：Godot **支持导出时自动代码签名**，需要 **Windows SDK**（在 Windows 上）或 **osslsigncode**（其他系统）+ **package signing certificate**。设置两处：编辑器设置 `Export > Windows > Sign Tool`；导出预设 `Options > Code signing`（`Enabled=true` + `Identity=证书`）。CI 环境变量：`GODOT_WINDOWS_CODESIGN_IDENTITY_TYPE` / `_IDENTITY` / `_PASSWORD`。

> ⚠️ **未验证**：该官方页面**完全没有出现 "SmartScreen" 字样**，也没有讨论「未签名 exe 弹出『Windows 已保护你的电脑』」的后果。网上关于「需 EV/OV 证书 + 累积信誉才能消除警告」的说法**本次未找到官方引文**，不要当作已核实事实引用。
>
> **保守建议**：课程阶段交付用 **zip + 一段说明文字**（「未签名，提示未知发布者时点『更多信息 → 仍要运行』」），把这一点写进 README。公开发布再考虑证书——注意**证书是持续付费项**。

### 6.4 许可证义务速查（写 `素材来源与许可.md` 时对照）

| 许可证 | 必须做的 | 对我们的含义 |
|---|---|---|
| **MIT** | 保留版权声明 + 许可文本 | 本报告推荐的绝大多数库都是 MIT，**保留出处即可** |
| **Apache-2.0** | 版权/许可通知 **＋ 标注改动 ＋ 有 NOTICE 要一并携带** | 比 MIT 多两件事 |
| **BSD-2-Clause** | 版权/许可；**二进制分发时**须在「文档和/或其他材料」中重现声明 | 我们导出 `.exe` → **必须放随包文档/关于页**，只在源码仓库放不够 |
| **CC0-1.0** | **无任何义务** | Kenney UI Pack 属此类，最省事，仍建议登记来源 |
| **CC-BY-4.0** | 署名 + 版权 + 许可 + 免责声明 + **指向素材的 URI/超链接**；改动需标注 | 比「写个作者名」要求多；**必须给素材本身的链接** |
| **CC-BY-SA-4.0** | CC-BY 全部 ＋ ShareAlike：改编后必须用同许可 | ⚠️ 会传染改编后的素材 → **建议原样使用不改编** |
| **OFL-1.1** | 见 §6.5 | 字体首选 |
| **GPL / AGPL** | Disclose source + Same license + State changes | ⛔ **绝对不要引入**，见 §6.6 |

### 6.5 OFL 字体：四条被广泛误传的规则（已对照 OFL-FAQ 正文核实）

- ✅ **打包进游戏不会让游戏变成 OFL。** FAQ 1.3 原文：*"Only the portions based on the Font Software are required to be released under the OFL. The intent of the license is to allow aggregation or bundling with software under restricted licensing as well."*
- ✅ **可以卖含 OFL 字体的游戏**（FAQ 1.4 明确列出 "games and entertainment software"）。
- ✅ **不需要为「使用」字体而署名。** FAQ 1.1.2 原文：*"No. Font authors may appreciate being mentioned … but that is not required."* ← **与很多教程说的「OFL 必须署名」相反**。建议仍然在 credits 里感谢，但那是礼貌不是义务。
- ✅ **打包/内嵌时可以不必附完整 OFL 文本**（FAQ 1.10）；FAQ 1.20 建议**至少**在 About 框给出「版权声明 + 许可声明 + 许可文本」。
- ⚠️ 不能只卖字体本身（1.6）；**改了字体必须改内部名**（Reserved Font Name 条款，5.2/5.9）——即修改版不得继续叫 "Noto" 或 "Source"。
- 🤖 **与你们的「AI 使用日志」直接相关**：OFL-FAQ **1.25** 规定，用 AI/ML 从含 OFL 源文件的训练数据生成的**字体**「应被视为衍生作品」，**必须继续按 OFL 发布**。（FAQ 1.26：AI 生成的**非字体**图形等同普通使用，不受此限。）

### 6.6 GPL 与 `addons/` 子目录：一个必须说清的灰区

常见的自救说法是「GPL 插件只是放在 `addons/` 子目录里，算独立作品，不传染我的游戏」。**这个说法站不住：**

GPL-3.0 §5(c) 原文：*"You must license the entire work, as a whole, under this License to anyone who comes into possession of a copy. This License will therefore apply … to the whole of the work, and all its parts, **regardless of how they are packaged**."*

不过要诚实标注：§5 的标题是 *"Conveying **Modified** Source Versions"*，真正决定传染范围的是「衍生作品 / 基于」的界定，而 GPL-3.0 正文**没有**像 LGPL 那样给出清晰的「接口 vs 链接」界线。→ **原封不动的 GPL 插件被专有游戏引用并一起分发，属法律灰区，本报告标记为「未验证 / 有争议」。**

**可操作结论：**

- ✅ 课程项目**直接避开 GPL/AGPL**，成本最低、无争议
- ✅ 已引入就移除并重写，或准备把**整个项目以 GPL-3.0 释出**（对要署名的课程作业不划算）
- ✅ 安全替代：MIT / Apache-2.0 / BSD / MPL-2.0 / CC0 / OFL
- ⚠️ **引入前读仓库根 LICENSE 本体，不要信 README 的自述**。两个真实的坑：GUT 的 GitHub API `license` 字段是 `null` 但实际是 MIT（LICENSE 在子目录里没被自动识别）；反向的「README 写 MIT、LICENSE 写 GPL」仓库也真实存在。

**MPL-2.0 值得知道一下**（本次调研中唯一未被采用的弱 copyleft 选项）：它覆盖的是**单文件**——改过的 `addons/` 内文件要开源，**游戏主体不受影响**。将来若想要一个「文件级弱 copyleft」的库，MPL 是比 GPL 安全得多的选择。

### 6.7 许可证文本放哪（官方给 6 选 1，做到一个即可）

Credits 界面 / 专门的「开源许可」菜单 / `print()` 输出日志（iOS 不行）/ 随包文件 / 印刷手册 / 链接（官方认为指向许可页的链接 *"would be an acceptable way to satisfy the license terms"*）。

**省事技巧**：`Engine.get_license_text()` / `Engine.get_license_info()` / `Engine.get_copyright_info()`；把 Godot 的 `COPYRIGHT.txt` 一起分发并**重命名为 `GODOT_COPYRIGHT.txt`**。

> ✅ 好消息（官方原文）：*"Your games do not need to be under the same license. You are free to release your Godot projects under any license and to create commercial games with the engine."*
>
> ⚠️ **但别忘了 Godot 引擎自己的 MIT 文本**——这是最容易被漏掉的一条署名义务。
>
> 💡 而 Maaack 模板的 `credits_label.gd` **会自动读 `ATTRIBUTION.md` 生成滚动 credits**——把第三方许可写进那个文件，credits 页就自动有了。这正好服务策划案 §21 的交付要求。

## 11. 调研方法与取证说明

- 取证通道：GitHub REST API、仓库 raw README / LICENSE / `plugin.cfg` / 完整文件树、Godot Asset Library API、Godot 官方文档。
- **关键的官方文档取证技巧**：`docs.godotengine.org` 的 HTML 会被巨型侧边导航淹没导致 fetch 截断；改用 Sphinx 源文 `https://docs.godotengine.org/en/<ver>/_sources/<path>.rst.txt` 可拿到**纯正文**。本次 20+ 个官方页面据此核实。
- `raw.githubusercontent.com` 直连受阻时改用镜像读取原文；**所有许可证均逐字读过 `LICENSE` 全文**，未依赖仓库描述或第三方摘要。
- **本次调研修正了三个原任务设定中的错误**（记录在此以保证可审计）：
  1. 「JSON 整数会变浮点」属实，但更严重的是**数值全转 float → 64 位 uid 丢精度**，原设定未提及；

  3. 「DirAccess 绝对路径方法 4.3 才引入」**是错的**——逐版核对 4.0/4.3/4.7 后确认这些方法 **4.0 就存在**，存档 API 无版本迁移风险。
- 本报告合并自四份独立调研（存档系统 / 菜单 UI / 肉鸽子系统 / 存档规范与合规），原始报告全文见同目录：
